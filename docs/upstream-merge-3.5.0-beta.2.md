## 4. 建议的合并顺序

```
① 决策：更新模块走 A（跟随上游官网通道）还是 B（双通道并存）
        ↓
② 合并到本地 beta（不推送、不部署）
   - Rust 线：保本仓架构 + 接上游 WASM 插件宿主与官网更新
   - i18n 线：源 JSON 并集 + 重新生成
   - 前端线：源码语义合并 + 重建产物
        ↓
③ cargo check --all-targets + ui-islands/mobile 构建通过
        ↓
④ 确认 WASM 插件包可用（ProviderPlugin 仓库是否已出 3.5.x 的 WASM 包）
        ↓
⑤ 升版本号（3.4.3 → 3.4.4，本仓自己的版本线）
        ↓
⑥ 服务器部署（冷构建 40–60 分钟）+ 验证
        ↓
⑦ 旧镜像打回滚标签（吸取上次教训，见 docs/beta-deploy.md 第 8 节）
```

**关键卡点**：第 ④ 步。如果 WASM 插件包还没就绪，即使代码合完也不该部署——这正是我建议「先合到本地 beta、不部署」的原因。

## 6. 明确不建议做的事

- ❌ 直接合并后立刻部署：插件运行时换代，未配套 WASM 包时线上会失能；
- ❌ 为了减少冲突而丢弃本仓的 `masking` / `routing` 拆分 / `AccountEgress`：这些是历次合并明确保留的架构决策；
- ❌ 把上游「未验收」的订阅通道当作可用功能对外宣称。
